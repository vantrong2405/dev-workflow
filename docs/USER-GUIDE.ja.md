## タスクを始める

[インストール](INSTALL.md)後、対象リポジトリを開き、`/ak` に依頼を渡すか、
スキル選択画面で ak の start を選びます。

```text
/ak CSV エクスポートに現在のフィルターを反映する
/ak TICKET-123 https://tracker.example/TICKET-123
```

チケット ID は任意です。記録が必要な場合は `adhoc-…` を作成できます。
判断が必要な場合は同じ会話で返答してください。独立した成果に分けられる大きな依頼は、
分割案を確認した後、依存順に処理します。

## プロジェクトの初回

エージェントは関連するリポジトリの指示、設定、スクリプト、CI、実装入口を読み、
`~/.workspaces/<slug>/PROJECT-FORM.md` に次回も使う情報を記録します。
普段の作業ルールを尋ねられたら、規約名や最近のタスクの進め方を伝えてください。
提示されたルール案に同意した内容が保存されます。質問をスキップして続行することもできます。

次のタスクは必要な項目だけを再利用し、不足や変更があった箇所だけ更新します。
タスク限りの例外はその作業ログに記録します。`/ak:learning` で項目や作業ルールを更新し、
`/ak:coaching` で業務知識を訂正できます。

## 作業の流れ

| 段階 | 内容 |
|---|---|
| 理解 | 要件、対象コード、リスク、受け入れ条件を確認する |
| 実装 | 決めた範囲を実装し、必要な実行結果を記録する |
| 検証 | 差分をレビューし、問題を直す。同じ入力とソースを検証済みの結果は再利用する |
| 引き渡し | 変更、検証結果、不足を報告する。通常は G8 まで進める |

UI の不具合は修正前にテストデータとクリック手順の図を用意します。利用者がブラウザで
再現するか、ak に実行を委任します。対応している場合は不具合に適した英語 UI を優先します。
修正後は記録済みの UI ケースすべてを検証し、見た目が変わる場合は承認済みの基準画像と比較します。
必須の結果がそろうまで該当ゲートを通過できません。[UI の検証手順](../references/ui-verification.md)

P0（金銭、権限、個人情報、既存データ、不可逆な移行）は、セキュリティ記録と
着手前の担当者・PMの G3 確認が必要です。通常の P1/P2 は要件が明確であれば別途
G3 を要求しません。`--strict` を指定すると対象ゲートが厳格になります。

`--ship` を指定すると同じ会話でリリース準備を続けます。G3 と strict G9 が必要で、
P0/P1 はさらに人による AUDIT の確認が必要です。P2 の監査を省略できる場合は理由を
記録します。push、merge、deploy には明示的な権限が必要です。

## 個別のコマンド

- `/ak:learning`、`/ak:coaching`、`/ak:decompose` で、学習、業務知識の訂正、分割を行えます。
- `/ak:spec`、`/ak:clarify`、`/ak:confirm`、`/ak:plan` で要件や計画を個別に操作できます。
- `/ak:redteam` は実装前に計画の前提、影響範囲、検証の抜けを確認します。
- `/ak:build`、`/ak:review`、`/ak:fix`、`/ak:test` で実装と検証を個別に操作できます。
- `/ak:check`、`/ak:ship`、`/ak:audit`、`/ak:status`、`/ak:clean` で各種判定、進捗確認、保存ができます。
- `/ak:feedback` は ak の問題報告に、`/ak:flow-diagram` は UI フローの整理に使えます。

作業ログは `~/.workspaces/<slug>/worklogs/<ticket>/` に保存されます。実行結果は
`06b-test-evidence.md` で参照できます。詳しくは [ステージ契約](../references/stage-contract.md)、
[リスク規則](../references/risk.md)、[CI テンプレート](../templates/ci/github-actions-ak.yml) を参照してください。
